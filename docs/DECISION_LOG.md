## D17 — 2026-10-01 · Supabase GoTrue 503 recovery (blocked — free plan limitation)
- **Trigger:** GoTrue crashes on startup with `sessions_timebox: 0` (invalid duration), returning 503 for all `/auth/v1/*` endpoints. Google OAuth cannot be verified while GoTrue is down.
- **Investigation:**
  - Free plan Management API PATCH returns 402 for `sessions_timebox` → nonzero (Pro plan required).
  - Setting `sessions_timebox` to `null` is accepted by the PATCH response but reverts to `0` immediately on GET (platform config service overrides to `0` on free plans).
  - Setting `GOTRUE_SESSIONS_TIMEBOX` as a secret via `supabase secrets set` does not affect GoTrue — secrets are only available to Edge Functions, not the GoTrue service.
  - `supabase config push` with local `config.toml` (`timebox = "24h"`) returns 402 (free plan blocks config push).
  - Project restart returns HTTP 200 but GoTrue remains down after restart.
  - `auth.instances` table's `raw_base_config` is platform-managed and empty in user-accessible tables.
  - Support ticket creation endpoint (`POST /v1/projects/{ref}/support/tickets`) returns 404 — no programmatic support access available.
- **Root cause:** The Supabase free tier forces `sessions_timebox: 0` via the platform config service after every restart. GoTrue interprets `0`/`0s` as an invalid duration and crashes on startup. This cannot be fixed programmatically on the free plan.
- **Decision:** Accept that GoTrue remains 503 on the free plan until either (a) the project is upgraded to a Pro plan (enabling `sessions_timebox` to be set to a valid duration), or (b) Supabase support manually resets the config at the platform level. All code paths (Google OAuth config, redirect URIs, callback route, middleware) are in place and correct — they will work once GoTrue recovers.
- **Impact:** Google OAuth verification is BLOCKED at the platform level; all application code is complete and verified via unit tests.
- **Verification:** See Phase 4/9 evidence — auth config GET shows `external_google_enabled: true`, correct `client_id`, `site_url` = `http://localhost:64820`, `uri_allow_list` includes both `localhost:3000` and `localhost:64820` callbacks. GoTrue returns 503 on `/auth/v1/settings` and `/auth/v1/authorize`. Project status `ACTIVE_HEALTHY` at platform level despite GoTrue crash.
- **Status:** adopted (platform limitation, not a code issue).

## D20 — 2026-10-02 · Root cause of PGRST301 (provider never registered) + orders subtotal fix
- **Trigger:** D19 escalated `PGRST301 "No suitable key or wrong key type"` to Supabase and Clerk as a suspected vendor-side fault. Opening **Project Settings → Authentication → Sign in / Providers → Third-Party Auth** showed the provider list **empty**. The Clerk provider had never actually been registered.
- **Root cause (verified):** Supabase's "Add new Clerk connection" form rejects a bare domain — its hint is `https://clerk.example.com or https://example.clerk.accounts.dev` and it validates that development Clerk domains must be entered **as a full `https://` URL**. Every previous attempt (including the re-registration described in D19) was refused by that validation, so no provider entry was ever stored. PostgREST therefore had no Clerk key in its keyset and could not match the token's `kid` — hence "no suitable key". D18/D19's belief that the provider was registered and re-registered on the bare domain was **wrong**; it is corrected here.
- **Same cause, second symptom:** Clerk's session tokens also lacked `role: "authenticated"`. Clerk's Supabase integration had been Enabled all along, but it only emits the claim once Supabase is genuinely connected. Immediately after the domain was registered correctly, the next `getToken({ skipCache: true })` mint returned a claim set containing `role: "authenticated"` for the first time. One misconfiguration, two blockers.
- **Verification (2026-10-02 22:09–22:10 UTC):** fresh session token `RS256`, `kid=ins_3K78jOMcVqWlJiAg3s2Wj8673Oa`, `iss=https://clear-clam-6319.clerk.accounts.dev`, signature verified against the live JWKS, `sub` = the Clerk user id, `role=authenticated` present. Exactly one authenticated Data API request (`POST /rest/v1/profiles?on_conflict=user_id`, anon key + Bearer token) → **HTTP 201**, one row returned with `user_id` equal to the Clerk user id. Because the write passed the RLS `WITH CHECK (auth.jwt()->>'sub') = user_id` on `profiles`, and every policy is `TO authenticated`, this single request proves **both** that `auth.jwt()->>'sub'` matches the Clerk user id **and** that the role is `authenticated`. No `service_role`, no RLS bypass, no forged token.
- **No support ticket was required.** Supabase and Clerk were not at fault.
- **Wedge reached:** the first real end-to-end order (22:12 UTC) persisted an `orders` row plus two `order_items` rows with catalogue prices. That exposed a second defect — see D21.
- **Security:** several secrets were captured in screenshots/paste during this investigation (Supabase legacy JWT secret, `sb_secret_` key, `service_role` JWT key, Clerk secret key, and a Vercel access token). ## D21 — 2026-10-02 · create_order could not persist subtotal (missing RLS UPDATE policy)
- **Trigger:** the first real order stored `subtotal = 0.00` while its `order_items` summed to 264.00, and the success page rendered "Total $0.00". Caught by the live wedge, not by tests — no test exercised the RPC as a Supabase-role caller.
- **Root cause:** `create_order` is `SECURITY INVOKER` (deliberate: RLS must apply) and finishes with `update public.orders set subtotal = v_subtotal where id = v_order_id;`. Migration `0003` created only SELECT and INSERT policies on `orders`. With RLS enabled and **no UPDATE policy**, Postgres filters the row out of the UPDATE: the statement matches **zero rows and raises no error**. The order therefore committed with `subtotal = 0` and the computed total was silently discarded. Verified with `pg_policies` on the live project (SELECT + INSERT only) before the fix.
- **Decision:** migration `0004` — (1) add the owner-scoped UPDATE policy using the same `auth.jwt() ->> 'sub' = user_id` check as every other policy; (2) narrow the `authenticated` role's UPDATE grant from the whole table to the single column the function writes (`revoke update … ; grant update (subtotal) …`). The anon key ships in the browser bundle, so without (2) a signed-in visitor could PATCH their own order row — status, totals, shipping address — directly against the Data API. Least privilege costs nothing here because the app never updates any other column.
- **Applied and verified 2026-10-02:** `orders are updatable by owner` present for UPDATE; `information_schema.column_privileges` shows `authenticated` may UPDATE exactly `subtotal`. Applied statement-by-statement because `supabase db query --linked` silently no-ops a multi-statement `begin; … commit;` block — the policy was absent after the first attempt and only appeared on re-run, so the verification query is the load-bearing part of this entry.
- **Evidence:** a fresh order placed through the real UI after the fix persisted `subtotal = 39.00` against `order_items` summing to 39.00 (`subtotal = sum(line_total)` → true), and `/order/success` rendered Subtotal $39.00 / Total $39.00. The two pre-fix orders were backfilled from their own `order_items` (`subtotal = sum(line_total)`); no order was deleted or fabricated.
- **Test gap (accepted, recorded):** unit tests cover the payload builder and validation but not the database's RLS behaviour, so this class of bug is only caught by a live wedge. A SQL-level regression check is listed in `IMPLEMENTATION_PLAN.md` rather than pretended to be covered.
- **Status:** fixed and verified live.

## D22 — 2026-10-02 · Paystack test-mode payments added (scope change, owner-instructed)
- **Trigger:** after the assignment form was submitted, the owner asked for Paystack to be added. Payments are **not** in the task brief and this repo had treated them as out of scope (`PRD.md` §32/§36 deferred them; invariant 9 recorded "no payment UI/states" as verified evidence). Per the source-of-truth hierarchy a newest explicit user instruction outranks the PRD, so the change was made deliberately and the PRD was amended rather than the conflict being ignored. The owner chose "proceed and amend" over "branch only".
- **Decision:** integrate **Paystack in test mode only**. A live `sk_live_…` key is **rejected at runtime** (`isLiveKey`) rather than trusted by convention, so this build cannot charge a real card even if misconfigured.
- **Flow:** `placeOrder` creates the order first (unchanged, `create_order`, trusted catalogue pricing) → `startPayment(orderId)` initialises a Paystack transaction → the customer pays → Paystack returns to `/checkout/verify` → that route **re-verifies the transaction against Paystack's API** and requires the verified amount to equal `toKobo(orders.subtotal)` → on success the order is marked `status=paid, payment_status=paid` and a receipt email is sent.
- **Money rule preserved:** the amount sent to Paystack comes from `orders.subtotal`, which `create_order` computed from the `products` table. No client-supplied amount is ever used, and the browser is never trusted — a hand-edited `?paid=1` cannot show a paid state because the success page reads `payment_status` from the database, not the query string.
- **No privileged bypass:** verification runs in a route handler using the Clerk session and the RLS-scoped Supabase client, so it can only ever touch the signed-in owner's own order. Migration `0005` adds `payment_reference` / `payment_status` / `paid_at`, a CHECK constraint, a partial unique index on `payment_reference`, and widens the `authenticated` UPDATE grant from `subtotal` alone to exactly the five columns the app writes. The owner-scoped policy from `0004` still applies; no `service_role`, no RLS weakening.
- **Honest degradation:** with no `PAYSTACK_SECRET_KEY` the order is still created and the success page says plainly that the store isn't set up to take online payment. No fake payment state is ever displayed.
- **Tests:** `tests/paystack.test.ts` — 13 unit tests over the pure helpers (kobo conversion and rounding, the live-key guard, initialize parsing, and verify parsing including amount-mismatch, abandoned, not-found and malformed bodies). ## D26 — 2026-10-03 · Rate limiting on checkout and the payment callback
- **Trigger:** the owner asked for abuse hardening on the checkout and payment-verify endpoints. Both were reachable by anyone who could sign in, and `placeOrder` writes a row and triggers an email per call, so a script could generate order rows and mail.
- **Problem with an in-process counter:** Vercel functions are serverless. Each cold start gets a fresh memory, and concurrent instances do not share state, so a `Map` in module scope is not a limit — it is a suggestion that resets whenever the platform feels like it. The owner chose **Upstash Redis (free tier)** over an in-memory limiter for exactly this reason, after being shown the weakness.
- **Dependency discipline (AGENTS.md §7).** `@upstash/ratelimit` + `@upstash/redis` would do two things: `INCR` and `EXPIRE`. The platform can already do that with `fetch`, and Upstash exposes both over a documented REST endpoint. **No package was added** — the calls are made directly, so the supply chain, install size and maintenance surface stay exactly as they were. Runtime cost is one extra HTTPS round trip on the two write paths. No license obligation (no dependency added), and no overlap with existing code.
- **Fails open, deliberately.** If the store is unset, unreachable, slow or returns something unexpected, the request is **allowed** and the failure is logged. Failing closed would mean an outage of a *rate limiter* blocks every customer from checking out — turning a defensive feature into a self-inflicted outage. The limits are abuse protection; **nothing about authorisation, pricing or RLS depends on them**, and the copy says so ("nothing was lost", which is true: the order is already durable when the callback is hit).
- **Keyed on the signed-in user where available**, falling back to the client address. `x-forwarded-for` is **sanitised, not trusted**: only the first hop is taken, it is length-capped at 64 characters and restricted to characters an address can contain, so a forged header cannot mint unbounded keys or inject separators into the key namespace.
- **Limits:** `place-order` 5 / 10 min, `start-payment` 10 / 10 min, `payment-verify` 30 / 10 min. Checkout is deliberately tighter than the callback it redirects to, since one order produces one callback. The verify route is limited because otherwise it is a free way to hammer Paystack's verify API; when limited it redirects with `payment=unknown`, which the success page already renders as "order saved, payment not completed" — no false payment state.
- **Pure logic separated from transport** (`lib/rate-limit-core.ts` vs `lib/rate-limit.ts`, `server-only`), matching the pricing/paystack split, so decisions are unit-tested without a network.
- **Tests:** `tests/rate-limit-core.test.ts` — 17 tests: boundary behaviour at and just past the limit, ceil-ed retry so nobody retries a millisecond early, missing-TTL falling back to a whole window instead of never expiring, `NaN` and `limit <= 0` failing open rather than blocking a customer, IP parsing and rejection of injected separators/newlines, key namespacing, rule sanity, and the user-facing copy (singular/plural seconds, minute rounding). ## D28 — 2026-10-03 · Structured cancellation reasons, with the biconditional held by a NULL-safe constraint
- **Trigger:** the owner asked to “do what is next” after `forge plan` classified **“Add order cancellation reasons”** as `feature / medium` with **zero approval gates**. It was treated as high-risk anyway: the task changes the signature of `set_order_status`, which D24 established as the **only** write path to `orders.status`.
- **The gap:** 0008 made `cancelled` reachable but recorded nothing about **why**. An admin could cancel an order and the only surviving fact was the status itself, which answers *is it cancelled?* and never *why?* That is the vague-state failure the design guidelines forbid, and it is unrecoverable after the fact.
- **Controlled vocabulary, deliberately with no `other`:** `out_of_stock` · `customer_request` · `payment_failed` · `address_unreachable` · `suspected_fraud`. Free text collects “n/a”, “cust. cancel” and `''`. A real case that does not fit is fixed by a reviewed migration, which is auditable; vague data cannot be un-vagged later. `suspected_fraud` exists because an order can be cancelled for a reason that is not the customer’s fault and must never be reported as one.
- **The biconditional** is enforced in the database, not only in the function:
  ```text
  status = 'cancelled'  <=>  cancellation_reason is a known value
  ```
  A cancellation with no reason is refused, and so is a reason on an order that is not cancelled. Because `cancelled` is terminal, the pairing can never drift later.
- **Function signature change — the genuinely dangerous part.** `set_order_status(uuid, text)` becomes `set_order_status(uuid, text, text default null)`. In Postgres, **`CREATE OR REPLACE FUNCTION` with a different argument list does not replace anything — it silently creates a second OVERLOAD.** Had the old function simply been left in place, two write paths to `status` would have existed, the two-argument one still granted to `authenticated`, still accepting a reasonless cancellation. The old overload is therefore **dropped explicitly** and privileges re-issued against the new signature. Verified: exactly one `set_order_status` exists, `security_definer = true`, arguments `(p_order_id uuid, p_status text, p_cancellation_reason text)`.
- **BUG FOUND BY THE PROOF, NOT BY REVIEW.** The first version of the constraint was
  ```sql
  check ((status = 'cancelled' and cancellation_reason in (...)) or (...))
  ```
  A SQL `CHECK` rejects only **FALSE** — a row whose expression evaluates to **NULL passes**. With a NULL reason the expression is `(TRUE AND NULL) OR (FALSE AND TRUE)` = `NULL`, so **a direct `UPDATE` created a cancellation with no reason and the constraint accepted it.** The fix is the load-bearing `cancellation_reason is not null`, which makes every reachable outcome `TRUE` or `FALSE`. This was caught by `supabase/verify/0010_cancellation_reasons.sql` assertion 6, which writes a cancellation **directly, bypassing the function**, and failed on first run. Reading the SQL would not have found it.
- **Backfill is a migration default, not observed truth.** Existing cancelled rows were backfilled from `payment_status`, which is a fact already recorded: `failed` → `payment_failed`, otherwise `customer_request`. Exactly one row qualified (`NGX-1006`, payment_status `failed`) and received `payment_failed`. No production order was cancelled, so no real reason was invented.
- **`cancellation_reason` is NOT added to the `authenticated` column grant.** The customer cannot write it, exactly as they cannot write `status`; the 0008 grants (`subtotal`, `payment_status`, `payment_reference`, `paid_at`) are restated unchanged.
- **TypeScript mirror:** `lib/orders.ts` carries the same vocabulary and a pure `checkStatusChange(from, to, reason)` used by the admin action. The duplication is deliberate and documented, as with the transition table. A blank or whitespace reason is rejected in TypeScript for the same reason SQL uses `btrim`.
- **UI asks rather than assumes.** [AdminStatusControl.tsx](../components/AdminStatusControl.tsx) keeps Cancel **disabled** until a reason is chosen, because a defaulted first option would let an admin record `payment_failed` on an order that was never paid. The reason is recorded for operations and is **not** rendered on the customer tracking page — “suspected fraud” is an operational judgement, not something to show the person whose order it is.
- **Verification:** `supabase/verify/0010_cancellation_reasons.sql` — 8 assertions in one self-cleaning block: no legacy 2-arg overload; missing reason refused; whitespace refused; unknown reason refused; reason on a non-cancelled status refused; valid reason stored; **the constraint holds without the function**; non-admin refused on the new signature; zero rows left behind. Passing, and it left **0** `user_local_verify_%` rows. One of my own unit tests also failed first — I had asserted `pending → delivered` was valid — and **the test was corrected, not the code**, since that transition is correctly refused.
- **Status:** applied live and verified. `tsc --noEmit` clean, `tests/orders.test.ts` **26/26**. The reason vocabulary is a product decision the owner may narrow or widen; the mechanism does not change.

## D30 — 2026-10-04 · Dark mode as a third axis, with all four appearances contrast-audited
- **Trigger:** the owner asked for "a proper dark mode with a full contrast audit of every accent color in both schemes."
- **A theme and a scheme are independent axes, so there are FOUR appearances**, not two: `datasheet/light`, `datasheet/dark`, `apple/light`, `apple/dark`. Auditing only the default would have left three of four unverified — which is the specific habit this project has been correcting. `datasheet/light` remains the default for a visitor with no preference.
- **THE STRUCTURAL DECISION: `ink` and `paper` simply invert.** Every dark palette defines ink as a light colour and paper as a dark one, and nothing else changes structurally. That single choice is what makes dark mode cheap and, more importantly, **correct by construction**: `text-ink` becomes light text, `bg-paper` a dark page, and critically `hover:bg-ink hover:text-paper` — the inverted-button pattern used in 17 places — flips to a light button with dark text with no extra class. A parallel set of `dark:` classes would have required restating every hover and inverted state by hand and would certainly have missed some.
- **No literal colours remain anywhere.** A sweep replaced all 16 `bg-white` card surfaces with `bg-surface` (pixel-identical in light, since `--color-surface` is `#ffffff` there) and all 18 `text-white` with `text-paper`. There are now no arbitrary hex colours, no `text-white`, and no `bg-white` in `app/` or `components/` — verified by grep, so a future hardcoded colour is a visible diff rather than an invisible regression.
- **THE BUG THIS WORK FOUND — and it was invisible until measured.** The primary buttons used `text-white`, a *literal*, while every other colour flowed through tokens. In the light schemes white-on-signal is 5.05:1 and fine; but dark mode turns `signal` into a **light** orange `#ff8a5b`, and white on that is **2.32:1** — a serious AA failure on the most important button on the site. It passed review, passed `tsc`, passed lint, and passed the build. It was caught by rendering the page and measuring the rendered button. Fixed by routing it through `text-paper`, giving **7.65:1**. Note the light scheme moves 5.05 → 4.56 in exchange; still above AA, and the trade is worth it for having one rule instead of two.
- **BUG FOUND BY THE GATE, NOT BY REVIEW: the bootstrap script stopped being valid JavaScript.** An edit left a stray `}`, making the entire pre-paint script a syntax error. It therefore **did not execute at all** — no theme, no scheme, every page fell back to unstyled defaults — and **every other gate stayed green**, because a script that never runs cannot fail a unit test that only imports a string. Three tests now close this: the script is compiled with `new Function`, executed against a fake DOM, and asserted to write both attributes. The gate that would have caught it (`bootstrap-script-parses`) was written, found to need fragile nested shell/JSON escaping, and **removed in favour of the unit tests**, which run inside the existing `unit` gate and need no escaping. A gate that is fragile is worse than no gate.
- **Scheme is resolved before paint, not in an effect.** The bootstrap script reads `matchMedia('(prefers-color-scheme: dark)')` itself and writes a concrete `data-scheme`. Doing it in React would paint light first and then repaint — for a visitor whose OS is dark that flash is the brightest thing on screen. Because the script already resolves `auto` to a concrete value, **the stylesheet needs no `prefers-color-scheme` media query at all**: exactly four token blocks keyed on attributes, instead of six blocks and a media query per combination.
- **`auto` is a live subscription, not a one-time read.** If the visitor leaves the page open and their OS flips to dark at sunset, the page follows. The `matchMedia` listener is attached only while the preference is `auto`, so an explicit choice costs nothing.
- **Preference and resolved mode are separate attributes.** `data-scheme-preference` holds `auto|light|dark` for the control; `data-scheme` holds the concrete `light|dark` for the CSS. Without that split the control would have to relabel "Auto" as "Light", which is a small lie that hides the fact that the setting is still following the system.
- **A malformed `?scheme=` resolves to `auto`, not to stored state** — same rule as `?theme=`, for the same reason: a broken link must be deterministic for whoever opens it.
- **`color-scheme` is set per scheme**, so the browser renders scrollbars, form controls and the default focus ring to match. This is the most visible way a dark mode looks unfinished, and it is easy to forget because nothing on the page itself is wrong.
- **Verification:**
  - `scripts/color-contrast-audit.mjs` measures **16 pairings across all four palettes (64 checks)** and **also greps `app/globals.css` for each audited hex** — without that, the audit and the stylesheet could drift and the numbers would describe a palette the site does not use. Replaces the apple-only script from D29.
  - `scripts/check-appearance-tokens.mjs` asserts both dark token blocks and the `color-scheme` declarations survive Tailwind compilation. The dark palettes live only in CSS; no type sees them, so nothing else would notice if they were dropped.
  - `tests/theme.test.ts`: **43 tests**, including all four palettes' contrast, the ink/paper inversion property, and the three bootstrap-script tests above.
  - `tests/e2e/theme-axe.spec.ts` now scans **all four appearances across 5 routes (20 scans)** and asserts `data-theme` *and* `data-scheme` applied before each scan. That assertion matters: a light-themed scan of a dark page still reports "accessible", so scanning the wrong scheme passes while proving nothing.
- **Known limitation, recorded not hidden:** the seeded product artwork is SVG with a cream background **baked into the asset**. In dark mode those images read as bright rectangles on a dark card. This is the same asset issue D29 recorded, now more visible; it is fixed by regenerating the imagery, not by CSS. Clerk's prebuilt sign-in component is also not themed — it renders its own light palette inside a dark page.
- **Status:** verified. `npm run verify` → pass. Axe: **zero violations across 20 scans**. All four appearances loaded in a real browser; the button contrast regression was measured before and after (2.32:1 → 7.65:1).

## D31 — 2026-10-04 · The Apple-versus-datasheet tradeoff: why two directions ship and which one is the product
- **Why this entry exists separately from D29.** D29 recorded *how* the second theme was built. It did not record the judgment: whether the Apple direction should ever replace the datasheet one, what each actually costs, and what evidence would change the answer. A decision that is not written down gets re-litigated every time someone opens the file, and the losing argument ("it looks nicer") is always easier to make than the winning one.
- **The trade, stated plainly.**

  | | `datasheet` | `apple` |
  |---|---|---|
  | Premise | the product is presented as a component datasheet — the document this audience already reads | near-monochrome product photography, space and surface instead of rules |
  | Buys | memorability, audience credibility, spec honesty | polish perception, familiarity, lower visual density, photography shown better |
  | Costs | reads as "technical" or dated to a mainstream buyer; higher visual density | **deletes the differentiator** |
- **The apple theme removes 11 identity-bearing elements**, all via `apple:hidden`: the `CATALOGUE 2026 · SPEC-FIRST GEAR` eyebrow, `SELECTED BY THE BENCH`, `07 GROUPS`, `00 PARTS`, the part number in every card strip, the `NG-0xx · CATEGORY · REV 2026-10` revision line, and the drafting dimension rule. It also drops mono-for-data in favour of the platform font. That is not restyling — it is the removal of the concept, in the same way removing a logo would be.
- **"Just copy Apple" is not actually available under this project's floor.** Apple's published `#007AFF` measures **4.02:1** on white and `#34C759` measures **2.22:1**; both fail WCAG AA as text, and AA is a hard requirement here, not a preference (AGENTS.md §4). The theme therefore uses darkened Apple hues. So the "Apple" direction was never available verbatim — this was always a choice between *Apple-like* and *datasheet*, not between copying and not copying.
- **The strongest evidence that the concept lives in the content, not the CSS.** The seeded product artwork is SVG with the datasheet's own drafting annotations and frame **baked into the image files**. The apple theme can remove every annotation the app draws, and those drawings still carry their frames and callouts. Making the apple direction fully coherent is not a CSS task — it requires regenerating the catalogue imagery. A concept that survives deletion of the entire styling layer is the load-bearing part of the product.
- **Decision: ship both, keep `datasheet` as the default, and treat `apple` as a comparison instrument rather than a candidate replacement.** The costs are measured and small: one component tree, one extra token layer, no duplicated pages, 64 audited colour pairings and 20 axe scans across four appearances. The benefit is that the claim "the datasheet concept is worth more than polish" is now *demonstrable* rather than asserted — a reviewer can open `?theme=apple` and see precisely what would be lost.
- **If forced to pick one, `datasheet` wins**, for three reasons in order of weight: (1) it is the approved direction in PRD §26 and DESIGN_GUIDELINES, and under the source-of-truth hierarchy an unapproved aesthetic preference does not overturn an approved requirement; (2) in a demo or review context the differentiation *is* the asset, and polish is table stakes rather than a differentiator; (3) removing it is irreversible in the way that matters — a datasheet store with the annotations stripped is a plain store, whereas an apple store that added part numbers back is merely a better plain store.
- **Revisit triggers — what would actually flip this.** Stated in advance so the decision is falsifiable rather than defended indefinitely:
  - The primary audience is general consumers rather than developers, makers and robotics learners. This is the only trigger that genuinely settles it, because it changes which premise is correct.
  - Real product photography on transparent backgrounds lands, removing the asset objection above and making the apple direction coherent for a fraction of the cost.
  - **The signal to watch:** if people describe the store as *hard to use* rather than *distinctive*, the tradeoff has tipped and `apple` should become the default. Confusion is a real cost and should not be dismissed as "they are not the audience". If the feedback is instead that it is memorable but not pretty, that is the datasheet concept working as intended.
- **Honest cost of this decision:** a reviewer who prefers the apple direction will see it as the worse product, because it is. That is the price of not optimising every surface for first impression, and it is a price this project accepted deliberately rather than by default.

## D32 — 2026-10-04 · Cart as a slide-over sheet, with the data layer left alone
- **Trigger:** the owner asked to turn the cart from a separate page into a slide-over sheet **without changing the cart data layer**. That constraint shaped every decision below.
- **`lib/cart/` is byte-for-byte untouched** — verified with `git status --porcelain lib/cart/`, which reports nothing. Open/closed is UI state with a different lifetime: it must not persist, must not survive a reload, and must never reach the serialised cart blob. Putting it in `CartProvider` would have meant threading a field through the store, its subscriber and its defensive parser for something that is not cart data. It lives in `lib/cart-sheet.tsx`, which imports nothing from `lib/cart/` — so no future change to the sheet can alter what is in the cart. A test asserts the localStorage key count is unchanged across open and close.
- **Built on the native `<dialog>` element with `showModal()`, not a hand-rolled overlay.** This is the load-bearing choice. The browser already provides modal semantics, a focus trap, Escape-to-close, top-layer stacking above every z-index, and focus restoration to the previously focused element. Re-implementing those is exactly how overlays end up letting Tab escape to the page behind, or stranding a screen-reader user. Verified: a real Tab press moves focus from the Close button to the product link and `dialog.contains(document.activeElement)` stays true.
- **BUG FOUND BY THE BROWSER — and it would have been severe.** Escape is handled by the **browser**, not by React: it closes the dialog and fires `close` without React state ever changing. The first version's close handler only restored focus, so after Escape `isOpen` stayed true — which meant the **page stayed scroll-locked forever**, `aria-expanded` still read `"true"`, and the open-effect would re-open the dialog on the next render. Fixed by treating the dialog's own `close` event as the authoritative signal and syncing state from it, so every close path (Escape, Close, Keep browsing, following a link) converges on the same state. Reading the code does not reveal this; only pressing Escape in a browser does.
- **Scroll lock needs `scrollbar-gutter: stable`.** Locking overflow removes the scrollbar, which reflows the page sideways. Reserving the gutter permanently means the lock is a no-op on platforms with classic scrollbars.
- **`CartLine` moved from `sm:` to `@md:` container queries.** This line now renders in two very different widths — the `/cart` page (~900px) and the sheet (~380px) — and `sm:` measures the **viewport**, so on a desktop it would have forced the wide horizontal layout inside a 380px sheet and overflowed. `@container`/`@md:` measure the container instead, so each context gets the layout that fits. This is the actual correct fix for a component reused at two widths; a `layout` prop would have been a worse answer that put the branch at every call site.
- **`/cart` survives as a real page.** A sheet cannot be linked to, so a shared or bookmarked cart URL must not 404. Both entry points exist and both are tested.
- **The e2e journey test was changed, deliberately and visibly.** It previously clicked `link[name="Cart"]` and waited for `/cart`. The control is now a button revealing a dialog, so that assertion would have hung. It now asserts `aria-expanded` toggles, the dialog appears, **Escape closes it and focus returns to the trigger**, and a separate test confirms the cart is fully operable by keyboard alone. This is a case where the test was updated because the behaviour changed on purpose — recorded here so it is not later mistaken for a test weakened to pass.
- **Status:** implemented and browser-verified — `:modal` true, 416px panel right-aligned, scroll lock applied and released, focus entering the dialog and returning to the trigger, cart line stacking correctly in the narrow container. `tsc --noEmit` and `eslint --max-warnings=0` clean; `tests/cart-sheet.test.tsx` 6/6. **Not yet committed.**

## D33 — 2026-10-04 · Product artwork carries no colour of its own, and is rendered as a mask
- **Trigger:** the owner asked to "make sure that the images are real". All eleven product images were checked first: every one returned 200 and rendered, so **nothing was broken**. The defect was different, and had already been recorded as a known limitation in D29 and D30 — the artwork carried light-mode colours baked in.
- **What was actually wrong.** Each SVG hardcoded its own palette: `#F6F3EC` as a **full-canvas background** in all eleven files, `#1A1D21` near-black strokes, and a `#8A939E` frame — the colour D14 had already rejected for text at 2.8:1. On a dark page that renders as a bright cream rectangle with invisible line art. It was not a cosmetic mismatch; it was the last light-locked surface on the site after D30 removed every other one.
- **Root cause: an `<img>`-loaded SVG is an isolated document.** Nothing the page does can reach inside it, so the artwork had no choice but to name its own colours — and could not follow the theme even in principle. Changing the markup around it could never have fixed it.
- **THE FIX: render the artwork as a CSS mask.** As a mask the SVG contributes only its **alpha**, and the visible colour comes from CSS (`--color-ink`). One file now renders as dark ink on a light surface and light ink on a dark one, with no second asset and nothing to keep in sync. Verified from real pixels: painted range **31..255** in light and **34..229** in dark — dark ink on light, light ink on dark.
- **Shading survives the mask because the artwork varies opacity, not hue.** Each product is drawn with gradients and layered shapes at different `fill-opacity` values, so the alpha carries the depth. This is why the files were redrawn rather than merely recoloured: a single-colour silhouette would have thrown away the only thing that made them look dimensional.
- **Annotations were removed from inside the artwork.** The old files carried `65% LAYOUT` dimension callouts and `NexaGear · NG-001` captions as `<text>` inside the image. That was the concrete reason the apple theme could never be coherent: the app could delete every annotation it drew and the drawings still had theirs. Captions now live in markup, where a theme can switch them off.
- **`next/image` is no longer used for product artwork.** These files are a few hundred bytes each; sending SVG through the image optimizer achieved nothing and added a code path.
- **Accessibility handled deliberately.** `ProductImage` takes an optional `name`. Present, it renders `role="img"` with that label; **absent, it renders `aria-hidden`** rather than `aria-label=""` — the difference between "an image with no name" and "no image at all". The cart row omits it, because the product name is already the link text and naming the image would make the row read twice. axe still reports zero violations across all four appearances.
- **Verification: `scripts/shoot-product-art.mjs`, and it caught its own false result first.** Two measurement bugs were fixed rather than worked around:
  - A plain **mean** luminance is dominated by whatever sits behind the letterboxed artwork, so it reported the *container* colour, not the artwork's. Replaced with a min/max range.
  - `boundingBox()` + `screenshot({clip})` sample **different coordinate spaces** once a page is scrolled, so the clip silently captured the wrong region. Replaced with `locator.screenshot()`.
  
  The check now reports a painted range and a count of distinct luminance buckets. A flat silhouette or an empty box fails. All **eleven** products pass with 13–15 buckets each.
- **Two rules written into DESIGN_GUIDELINES**, because both were learned by breaking them: *never put a hex in an SVG*, and *never bake annotations into artwork*. A third follows from D30 — never write a literal colour in markup either.
- **Honest limitation.** These are original vector renderings, not photographs. PRD §29 requires original or licensed imagery, and sourcing stock photographs is a licensing decision for the owner, not something to do unasked. What changed is that they are now shaded, product-accurate, theme-aware drawings rather than wireframes — a genuine improvement, but not the same thing as photography, and I am not claiming otherwise.
- **Status:** implemented and verified. All eleven files redrawn, zero hardcoded colours remaining (grep-confirmed), `npm run verify` → pass, axe clean across 20 scans. **Not yet committed.**

## D34 — 2026-10-04 · Page metadata is derived from one path, product shares get a real card, and the first-load budget is over
- **Trigger:** finishing the project, which `AGENTS.md` §9 defines as every box in `DEPLOYMENT_CHECKLIST.md` and `PRODUCTION_QUALITY.md` being `[x]` or `N/A` with a reason. Checking them properly meant measuring each claim instead of recalling it — and four of them were false.
- **What was actually broken (found by measuring the rendered HTML, not by review):**
  1. **`/` and `/shop` published no canonical at all.** The required "Canonical URLs" row was simply untrue for the two most important pages.
  2. **`/shop` published `og:url` pointing at the homepage**, so every share of the catalogue claimed to be the site root.
  3. **Product pages published no `og:image`, and their `twitter:title` was the site's, not the product's.** A shared product link rendered as bare text. This was the worst of the four, because a product share is the most likely share.

Nothing fails, nothing warns, and the build, the types, and the tests all stay green. This is a class of bug that cannot be caught by unit tests of the pages — only by reading the tags the server actually emits.
